# Third-party repository adoption audit

Retain the existing platform. No full-framework migration is justified by the inspected evidence.
Recommend only two small next-phase improvements: a Windows offline CI gate and a bounded local source map.
Both are proposals for review; this audit implements neither and installs no third-party package or platform.
Inspection date: **2026-10-24 UTC**. Source, licensing and maintenance conclusions are pinned below.

## What the five requested repositories actually offer

### TradingView-Webhook-Trading-Bot

Inspected [README](https://github.com/lth-elm/TradingView-Webhook-Trading-Bot/blob/e9efac27c4b5f933442e5248b7e180c176b6c47a/README.md), [Flask handler](https://github.com/lth-elm/TradingView-Webhook-Trading-Bot/blob/e9efac27c4b5f933442e5248b7e180c176b6c47a/app.py), [order router](https://github.com/lth-elm/TradingView-Webhook-Trading-Bot/blob/e9efac27c4b5f933442e5248b7e180c176b6c47a/orderapi.py), exchange adapter source, Discord handling and [dependency pins](https://github.com/lth-elm/TradingView-Webhook-Trading-Bot/blob/e9efac27c4b5f933442e5248b7e180c176b6c47a/requirements.txt). Complete 31-entry tree has **no LICENSE/NOTICE, test suite or CI workflow**. A public repository is not permission to copy its code. No source adoption is proposed.

The Flask handler parses unrestricted request JSON, compares a body passphrase using ordinary equality, then calls `order(data)`. The order router selects exchange/subaccount from input, keeps account/risk state in module globals and invokes exchange entry/exit logic. No signed freshness envelope, nonce/event uniqueness store, bounded schema/body size or durable research-only queue appears in that path. The README describes chat-approved trade relay; the checked-in Discord bot script is commented out. Neither the described relay nor that unfinished script establishes a safe research-only authority boundary. These are static findings, not claims that every possible external deployment lacks a reverse proxy.

**Unsafe or inappropriate:** copying the handler, exchange routing, mutable global risk/account selection, or chat-approved order behavior. It conflicts with single deterministic risk authority and the current prohibition on all external orders. **Future integration:** a separately implemented, default-disabled *non-executable signal inbox* only if an identified research use needs it. Nothing from this repository is needed for current data collection.

For that future scope, require HTTPS at a controlled ingress, verified sender authentication, strict versioned instrument/timeframe schema, UTC signal/bar time plus independent receipt time, maximum age/future skew, durable event deduplication across restarts, request/rate caps and append-only rejection reasons. Never accept account, quantity, risk-limit, shell or order commands. Never route an alert to `EntryRequest`, execution strategies or a broker. Repeated identical events must remain non-executable even after restart; replay tests must include changed IDs, same bar/strategy payload and clock skew.

TradingView's [official webhook documentation](https://www.tradingview.com/support/solutions/43000529348-how-to-configure-webhook-alerts/) describes POST delivery, account 2FA, ports 80/443 and a three-second processing deadline; it warns against passwords in the body. It does **not establish native arbitrary signature-header/HMAC support**. Therefore do not invent a TradingView HMAC feature: a trusted ingress may sign its internal envelope after authenticating the external request using a verified supported mechanism. IP filtering alone is insufficient authentication. Prove the actual sender/ingress mechanism and applicable plan before implementation; no paid plan was used. A fast durable acknowledgement does not turn delivery into exactly-once evidence or a broker quote. An alert alone also establishes no market-data storage permission.

Aider's failure-output/test feedback is a useful workflow idea, not evidence its defaults meet our gates: [test/run commands](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/commands.py) can run shell commands and add output to the chat; [argument defaults](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/args.py) defaults Git verification off, and [Git implementation](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/repo.py) adds `--no-verify` in that case. ## Why a full-framework migration is not justified

The current platform already owns the difficult project-specific boundaries: source/receipt time, prospective versus retrospective evidence, rights/retention refusal, split protection, shared causal features, funded deterministic risk, append-only journals and non-executable dashboards. Replacing them would require re-proving those invariants and migrating evidence/version histories. Two delayed M5 reference instruments do not present measured throughput pressure that justifies a native/distributed platform.

Superalgos adds a second executable visual trading stack; Nautilus adds risk/execution/account engines and currently requires a different Python version; PyBroker/vectorbt add another simulation representation and license review; Qlib duplicates experiment/storage workflows and conflicts with MLflow. Aider is developer tooling and Alpaca is a provider SDK, neither a replacement architecture. QuantStats can later be an optional report/parity layer without becoming authoritative.

A future isolated experiment could change the assessment only with a measured unmet requirement, independently verified rights, versioned semantic/parity tests, resource measurements and a reviewed migration plan that preserves a single risk authority. No such evidence was established here. Preserve current code; select methods and narrow interfaces only.
