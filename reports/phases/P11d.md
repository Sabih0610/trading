## Sealed forward operation

The owner's updated prompt explicitly authorizes recording now, sealing immediately
and opening once later in P14. It grants no historical back-fill or analytical read.
The collector records raw public XAUTUSDT depth/bookTicker JSON plus a current live
snapshot, marks both files and manifests `holdout: forward_sealed`, records API
terms (not Vision licence), collector start and code version, and resynchronizes
on transport loss/sequence gaps. It computes no price/spread/depth statistics.

Windows native ACLs deny ReadData on each empty new file before bytes are written.
Checksums are computed from in-memory write bytes; archived parts/manifests are
never reopened. Central guarded readers, paths, sidecars, frames and engine inputs
refuse seals, including callers claiming synthetic mode. Core holdout code is pinned
in research/paper source identities. No unseal command or final-test bypass exists.

Only a separate health JSON is readable: heartbeat, uptime, connection state,
static error category, gap count, reconnects and bounded file-size history. All
runtime outputs are ignored by Git. Capture-only registry metadata explicitly says
`admitted_for_research: false`; it invents no reviewer approval. API terms expose no
verified version string in the checked public pages; resolve rights before P14.
See [ADR 0020](../../docs/adr/0020-sealed-forward-book-capture.md).

health. Current scheduled task: **TradingBot-P11d-Sealed-XAUT**, running from the
stable task worktree. The hidden-helper transfer and later native-ACL deployment
created new capture sessions; no lost interval was back-filled. Hard process death
