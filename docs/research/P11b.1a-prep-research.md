# P11b.1a-Prep research — secure owner-assisted onboarding

Inspected 2026-10-27 UTC. Public documentation only; no authentication or token endpoint called.
Implement a small owned-tested onboarding boundary; preserve the quote facade, message allowlist,
paper engine and all rights/risk gates. No new SDK, runtime dependency or copied upstream source.

| Question | Options | Decision |
|---|---|---|
| Correlation | Assume state/PKCE; cookie alone; exact unpredictable registered URI | Docs/SDK do not establish state/PKCE. Require a fresh random callback path registered exactly by owner for each attempt. Consume before exchange. No wildcard/dynamic registration assumption. Cookie alone does not bind an authorization code. |
| Token transport | Generic SDK defaults; unrestricted URL; fixed HTTPS exchange | Official SDK defaults to trading and exposes a base URI option. Do not adopt it. Own fixed host/path, no redirects/proxy/debug URL logging, bounded response and sanitized errors. |
| Scope evidence | Infer from requested scope/account rights; verify actual returned field | Dedicated enum parsers and returned token permission plus exact single-demo grant, broker and owner account confirmation. Account FULL_ACCESS can coexist with a view-only app token. |
| Credential persistence | Separate token JSON; root .env transaction | Existing names retained; private ACL before reading/staging, locked atomic replace/fsync, complete token pair and pin together. Authorization codes only in one-use memory. No token artifacts or automatic refresh. |
| Integration | Merge OAuth into old checkout; isolated superset of validated platform | Prep branch from phase-P11b.2a.1-done. Written ordered integration plan; original worktrees untouched. Genuine-input consumer remains absent. |

## Verified provider requirements and limits

[Application registration](https://help.ctrader.com/open-api/api-application/), accessed 2026-10-27:
approval precedes integration and redirect setup; Playground redirect is unsuitable for an application.
Owner must check actual approval and register the exact callback privately. Neither occurred here.

[Account authentication](https://help.ctrader.com/open-api/account-authentication/), accessed 2026-10-27:
documented authorization parameters are client_id, redirect_uri, scope, optional product. Select only
accounts. Codes expire after one minute; documented access lifetime is 2,628,000 seconds; refresh
tokens have no stated expiry and rotation invalidates old tokens. GET apps/token is documented;
the refresh example uses POST despite the earlier GET table. Use the official SDK's GET shape for
both grants, record the discrepancy, and leave genuine behavior unverified. No automatic refresh.
No documented state/PKCE or loopback random-path acceptance was established. Do not claim support.

[Official SDK auth source](https://github.com/spotware/OpenApiPy/blob/e944996e6fe9436b8b4a1b668da4ac41a826bb85/ctrader_open_api/auth.py),
MIT, existing source pin: GET exchange/refresh with query parameters; default trading scope makes
direct adoption inappropriate. Credentials can occur in URLs internally; our transport never sends
those URLs to a browser, logger or exception. TLS/proxy/debug limitations and local-admin threats
remain explicit; this is not proof against malicious process instrumentation.

[Pinned model schema](https://github.com/spotware/openapi-proto-messages/blob/3fd8bddfbe0cfc2ecfda079623dc4e498af11e66/OpenApiModelMessages.proto)
and [message schema](https://github.com/spotware/openapi-proto-messages/blob/3fd8bddfbe0cfc2ecfda079623dc4e498af11e66/OpenApiMessages.proto),
MIT, accessed 2026-10-27: separate token and account enums. Account-list permissionScope is optional
in the wire schema but locally mandatory for safety. Missing account accessRights is explicitly
unknown locally, despite the protobuf default; never infer token permission from it. Preserve the
existing fixed read message set; onboarding needs only application auth, token account listing,
account auth and trader identity. No quotes/subscription or order messages.

## Correlation tradeoff and remaining security boundaries

Every prepared callback gets 256 bits of randomness in its exact registered path; one owner-started
session consumes it even on timeout/error/crash. Another attempt requires a fresh registration.
This is a locally validated capability-based correlation measure, not provider state/PKCE support.
Keep the private path unshared. It cannot defeat a malicious local administrator, compromised
browser, leaked registration URI or stolen code. Exact portal URI acceptance and browser behavior
require later approved evidence. Never relax to a fixed guessable callback or undocumented echo.

Source timestamps, actual bid/ask, broker costs/units, data storage rights, regional/legal and
independent Shariah eligibility remain separate prerequisites; successful OAuth alone proves none.

Implementation references, accessed 2026-10-27: [Python 3.12 HTTPS](https://docs.python.org/3.12/library/http.client.html),
[local HTTP handler](https://docs.python.org/3.12/library/http.server.html) and
[Windows icacls](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls).
The stdlib server is used only on ephemeral, bounded loopback sessions. Override parser error
responses as well as request logging; default error pages can reflect credential-bearing targets.
The private prepared URI is bound to its accepted code locally before any exchange. Both hazards
were reproduced by owned failing tests and corrected; no generic OAuth SDK is installed.
